# Window screenshots through MCP

Maintainer note: `.temp/tests/` contains optional, disposable local harnesses, excluded from public downloads. Commands below require those retained harnesses; historical evidence is not shipped or regenerated by a build.

`capture_windows` lists windows; `capture_screenshot` returns one selected window as a standard MCP PNG image block with text metadata. `capture_sequence` returns alternating metadata and PNG blocks for 2–16 frames from the same window. Image bytes travel through the configured MCP transport. No screenshot files, scripted bridge, native hooks, desktop capture or external helper are used by the server.

For motion inspection, call `capture_sequence` with `windowId`, optional `frameCount` (default 8), and `maxDimension` (default 1280; 320–3840). Frames are copied before PNG encoding. Use `frameSystemRelativeTicks` (100 ns units) to measure actual intervals; the tool does not guarantee a capture frame rate or every rendered frame. `capturedAt` records when each frame was acquired by the server. Sequences share screenshot selection validation and the single capture gate, with a ten-second deadline, 256 MiB source-frame budget and 64 MiB combined PNG budget. An oversized sequence fails explicitly; request fewer frames or smaller output as appropriate.

## Setup and use

Set `captureExecutables` in your `configuration.json`, using the single `configuration.example.json` as a reference. Each entry maps a label to an exact executable path. The configured `workbench.executable` is included automatically as `workbench`; do not repeat it. `targets` remains solely native-analysis configuration and does not enable capture. No Ghidra/Java is needed for capture.

Paths resolve relative to the configuration file and support the existing environment and `${Documents}` expansion. Labels are unique ASCII letters, digits, hyphens or underscores, 1–64 characters; `workbench` is reserved. Duplicate executable paths are rejected. Remove example entries for installations you do not have. `--check-config` checks these paths without capturing anything.

1. Call `capture_windows` with no arguments.
2. Select the entry by target, process ID and title. Multiple clients with identical titles have separate process IDs and window IDs; multiple windows within one process are also distinct.
3. Call `capture_screenshot` with `{"windowId":"<returned ID>"}`. Optionally set `maxDimension` to 320–3840; the default is 1600.

The response contains an `image/png` image block and metadata: target, PID, executable, current title, completion timestamp, frame system-relative ticks, source/output dimensions and backend. Images preserve aspect ratio and are never enlarged. The server does not interpret the pixels or infer editor/game readiness. Clients must support MCP image blocks to display them.

Only visible top-level windows belonging to configured executable paths are listed, including separate editor/dialog windows. A screenshot covers **one** window; separately owned dialogs are not composited over it. Select a dialog's own entry when needed. Native title-bar appearance and sizing can differ between windows due to DPI and application rendering.

IDs are scoped to this server session. They expire after five minutes, on the next `capture_windows` call, or server restart. Each selection binds to the original Windows capture item at listing time and is invalidated by its `Closed` event. A screenshot uses that original item rather than recreating one from a potentially reused window handle. The server also rechecks process identity (start time and executable), window ownership and visibility before and after capture. List again after closing/reopening a window.

## Behavior and limits

There is one backend: **Windows Graphics Capture**, targeting a window through `IGraphicsCaptureItemInterop`. It uses a hardware Direct3D 11 device and a free-threaded capture pool. No activation or focus change is performed; another window covering the target does not become the captured content. The cursor is omitted. Windows may show its normal capture border.

This build targets **Windows 10 version 2004/build 19041 or later, x64**. Capture also requires an interactive desktop and working hardware graphics/capture support. OS restrictions and protected content can prevent capture or produce blank content. There is no software-renderer or alternate capture backend.

- Minimized and cloaked windows are rejected. Restore the window explicitly; capture does not restore it.
- Closed, expired or unknown selections fail. No other window is substituted.
- Before retaining the first frame, the pool can reconcile one difference between the selected item's size and the frame's content size (for example, maximized-window borders). It discards that frame and recreates the pool at the observed content size. Metadata reports `selectionWidth`, `selectionHeight` and `initialGeometryAdjusted`. Any further size change, or resizing after a frame is retained, fails explicitly; no sequence mixes dimensions.
- One capture runs at a time; a concurrent request returns busy.
- Frame wait and asynchronous conversion/encoding share a ten-second cancellation deadline. Synchronous Windows/driver calls are outside that asynchronous deadline.
- Source frames are bounded at 33,177,600 pixels; encoded PNGs at 16 MiB.
- A static, old-looking or blank image may be what the application is rendering. Successful capture means a frame was returned, not that a game finished loading or a project initialized.

## Implementation references

Microsoft documents [CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [free-threaded frame pools](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded), [surface copying](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.imaging.softwarebitmap.createcopyfromsurfaceasync) and [bitmap encoding](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.imaging.bitmapencoder). The C# implementation uses the Windows SDK projection and small C# ABI declarations, not a second capture service.

The initial geometry reconciliation follows Microsoft's [ContentSize](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe.contentsize) and [frame-pool Recreate](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.recreate) contracts. Undefined surface padding is never returned as image content.

## Reproducing validation

Build the solution, then run the test-owned overlapping-window fixture:

```text
dotnet run --project .temp/tests/ReforgerMcp.CaptureTests -c Release --no-build -- <server-dll-or-exe> fixture <fresh-evidence-directory> fixtures
```

It checks real MCP image serialization, decoded PNGs, correct pixels despite overlap, separate windows, stale selection rejection, same-process window replacement, minimized/closed rejection, cancellation, concurrent busy behavior and repeated capture. It closes only its own fixture process.

For running Workbench/game windows:

```text
dotnet run --project .temp/tests/ReforgerMcp.CaptureTests -c Release --no-build -- <server-dll-or-exe> <capture-config.json> <fresh-evidence-directory> real
```

This saves the image blocks and metadata for visual review. It does not launch or close the configured applications. See [system validation](system-validation.md) for observed coverage and exclusions.
